<objective>
Prove the entire Phase 3 data plane on one path, end to end, in a single commit: a date of birth
is checked, six consent rows are seeded, one bleed is logged through an encrypted Dexie write whose
key lives in the device keystore, and the cycle view renders that day count against her own
historical range with a confidence band and none of the banned framing.

Purpose: this phase's two hardest architectural risks — the native-keystore encryption bridge and
the irregular-native copy contract — are both cheapest to discover on the first commit and most
expensive to discover on the tenth. The tracer buys that discovery. Every other plan in this phase
expands horizontally from the slice this plan proves.

Output: a running test harness, a typed Dexie schema at version 1, the consent ledger, the native
secure-storage bridge, the age gate, and the two thin screens that close the loop.
</objective>

<phase_assumptions>
These are planner decisions, made explicitly rather than defaulted silently. They bind every plan in
Phase 3. Each is recorded here because a later reader will otherwise assume it was an oversight.

**A-01 — Encryption architecture: Option B (native keystore-backed key), not Option A.**
Research finding #2 offered a documented scope-narrowing (accept OS full-disk encryption and defer
the literal keystore language) or a native secure-storage bridge now. This plan takes the bridge.
Three reasons, in order of weight:
1. ADR-001 is LOCKED and already names the native plugin set as "camera, OCR and **encrypted
   storage**". Option A would contradict a locked ADR, which the planner has no authority to do.
2. PRIV-05 is a Phase 3 requirement, not a Phase 6 requirement. Narrowing it here would be scope
   reduction of a requirement this phase owns.
3. It is the one-way door. Retrofitting encryption later means a Dexie migration over eighteen
   months of exactly the data the product's core value depends on.
Recorded against research Assumptions Log A4, which this decision reverses in favour of the literal
requirement.

**A-02 — Voice on-device guarantee: option (a), a native plugin patch, with option (b)'s radio-off
protocol retained as the verification gate rather than as the architecture.** Full reasoning is in
`03-05-PLAN.md`, where the decision checkpoint sits; noted here so the schema and native-bridge
conventions established by this plan anticipate a second native bridge.

**A-03 — Native plugin work is assigned to Dhodraj, not Rahul.** The research flagged that patching
a Capacitor plugin's native source falls outside all four fixed role scopes. The split taken here:
Dhodraj owns what the native code *does with data*, because "audio never leaves the phone" and
"the key lives in the keystore" are data-plane guarantees and the data plane is his. Rahul owns
whether the patch *builds and stays applied* — patch reproducibility, the macOS runner, the device
run — because that is build and toolchain. This keeps "never the UI" intact and gives Rahul the
half of the problem that is genuinely DevOps.

**A-04 — Age gate: self-declared date of birth with a hard block, and nothing more.** Research
finding #5 flagged the legal sufficiency of self-declaration as genuinely contested and LOW
confidence. This plan builds the simplest defensible version and does not attempt Aadhaar, document
upload, or any third-party age-assurance vendor — over-collection would itself be a
data-minimisation problem. **This may need revisiting once the CDSCO/DPDP pre-submission opinion
that OPEN-05 already calls for comes back.** That revisit is recorded, not resolved, here.

**A-05 — Directory ownership follows the team's own build plan**, which is authoritative on this
point: `src/core/` is Dhodraj's, `src/app/` and `src/ui/` are Belson's, `ops/` and CI are Rahul's.
The research document proposed a different layout (`src/db/`, `src/features/`); it is mapped onto
the team's boundaries rather than replacing them, so no one has to work outside their scope.
</phase_assumptions>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 3: Encryption architecture — one-way door</name>
  <decision>
    Where does the key that encrypts the local health database live: in the device's hardware
    keystore behind a native bridge, or in JS-managed memory with OS full-disk encryption treated as
    sufficient for this phase?
  </decision>
  <context>
    PRIV-05 and NFR-301 say "AES-256 with keys in Secure Enclave or Android Keystore". Research
    established that neither Dexie nor `dexie-encrypted` provides that — `dexie-encrypted`'s own
    documentation never mentions Keystore or Secure Enclave, and its key guidance is entirely
    software-based.

    This is a one-way door. The database this decision shapes will hold eighteen months of check-in
    history — the exact data the product's core value depends on. Changing the answer later is a
    Dexie migration over live user data, not a config change.

    The planner's recommendation is option-b-native-bridge, recorded as assumption A-01 above, on
    three grounds: ADR-001 is LOCKED and already names "encrypted storage" in its native plugin set,
    so the alternative contradicts a locked decision; PRIV-05 is a Phase 3 requirement, so narrowing
    it here is scope reduction of work this phase owns; and PROJECT.md records that this product is
    already **behind** PMOS Vera on privacy and must never lead with privacy as a differentiator —
    shipping less than the requirement's stated language is the specific gap a security review finds.
  </context>
  <options>
    <option id="option-b-native-bridge">
      <name>Native keystore-backed key (recommended)</name>
      <pros>Satisfies the requirement's literal language. Consistent with LOCKED ADR-001. Defends against the rooted-device tampering threat that OS disk encryption does not cover once the device is unlocked. No migration later.</pros>
      <cons>Adds a native plugin dependency and a Kotlin/Swift surface to Phase 3. Adds device-only test surface that Node cannot cover.</cons>
    </option>
    <option id="option-a-os-encryption">
      <name>OS full-disk encryption, documented scope narrowing</name>
      <pros>No native work this phase. Ships faster.</pros>
      <cons>Contradicts LOCKED ADR-001. Narrows a Phase 3 requirement without authority. Leaves the rooted-unlocked-device threat unmitigated. Retrofit later is a migration over the most valuable data in the product.</cons>
    </option>
  </options>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input -> Dexie write | Date of birth and bleed data cross from an untrusted form into the persistent store |
| JS runtime -> native keystore | The encryption key crosses the Capacitor bridge; JS must never retain it beyond use |
| device filesystem -> IndexedDB | On a rooted or jailbroken device an attacker reads the IndexedDB files directly |
| npm registry -> build | Package installs pull third-party code into a health application |

| T-03-01 | Information Disclosure | src/core/db/crypto.ts, src/core/native/secure-storage.ts | critical | mitigate | Master key generated inside and held by the platform keystore; never written to localStorage, IndexedDB or Preferences. Acceptance criterion asserts no persistent key write exists. |
