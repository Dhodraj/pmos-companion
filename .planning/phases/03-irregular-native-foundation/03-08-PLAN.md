<objective>
Give her the four rights that make this a product she can trust with the most sensitive data she
has: see what is held, take it away, delete it entirely, and decide class by class what is collected
in the first place.

Purpose: PRIV-01 and PRIV-02 are the requirements that a security review reads first and that a user
never thinks about until the day she needs them. Both fail in the same way — quietly, by being
almost complete. An export missing one table and a delete leaving one key behind both look like
success from the outside.

Output: the consent surface, the data-rights surface, the mycyclesafe import and the quiet-hours
control.

Owners: Dhodraj Sundaram on export, erase and import; Belson Johnson on every screen;
Satheeshkumar reviews the consent flows, which his role scope names explicitly.
</objective>

  <behavior>
    - The export contains every table declared in the schema, enumerated from the schema itself, so a
      table added later is included without editing the export function.
    - The export of a seeded database round-trips: importing it into an empty database reproduces
      every record.
    - The export of an empty database produces a valid document rather than failing.
    - Deletion leaves every table empty, verified by enumerating tables from the schema.
    - Deletion destroys the keystore key, and a subsequent open generates a new one rather than
      recovering the old.
    - Deletion is idempotent — running it twice does not throw.
  </behavior>
  <action>
    Use `dexie-export-import`'s schema-introspecting export. Do not write a function that iterates a
    list of known tables. Research names this precisely: a hand-maintained list silently misses any
    table added after the function was written, and that gap is invisible until an audit. Phase 4
    adds tables. This function must already cover them.

    Write the resulting blob through Capacitor Filesystem and hand it to the share sheet, so a
    one-tap export has a destination rather than being a blob in memory. The format is
    machine-readable per PRIV-02 — the export is data she can take elsewhere, not a PDF she can only
    look at. The clinician-facing PDF is a different artifact and lives in plan 03-07.

    `erase.ts` deletes the database and then destroys the key held in the platform keystore. Both.
    A wipe that leaves the key behind has not deleted her data in the sense the requirement means,
    and it is exactly the kind of almost-complete that passes a casual test.

    On the 72-hour clause: honour it trivially and provably. Health records live only on the device,
    and plan 03-04's network-surface allowlist means Phase 3 adds no route that could hold a copy —
    so deletion is complete the moment it returns. Record that reasoning in the summary rather than
    leaving a future reader to wonder whether a server-side deletion job was forgotten.

    Write `tests/db/export-delete.test.ts` first, enumerating tables from the schema in the assertion
    itself so the test strengthens automatically as the schema grows.
