<objective>
Make the phase's privacy guarantees properties of the build rather than properties of everyone
remembering. Stand up CI, enforce the bundle and performance envelope, assert the two things that
must never be true in this codebase, and prove the native keystore bridge on real hardware.

Purpose: PRIV-03 and PRIV-05 are the two requirements in this phase that fail silently. Nothing
breaks when an analytics SDK is added; nothing breaks when a patch stops being applied. Both are
found in an audit, months later, or not at all. CI is the only thing that finds them the same day.

Output: a CI workflow, two privacy guards, a bundle budget, and a recorded device smoke procedure.

Owner: Rahul Ramakrishnan. This is the plan that owns "it runs on the phone" for Phase 3, the same
scope he holds for the weekend build.
</objective>

  <files>ops/ci/privacy-guard.mjs, ops/ci/allowed-network-surface.json, .github/workflows/ci.yml</files>
  <action>
    Two assertions, both in one script, both structured so that free-form source text can never
    satisfy or break them.

    **Assertion A — dependency and import ban.** Read the dependency and devDependency *keys* from
    `package.json` as parsed JSON, and separately collect only lines matching an import or require
    statement from `src/`. Compare against a denylist of ad-tech and third-party health-analytics
    package families. Match on package name, so a substring appearing inside a comment or a string
    literal is structurally incapable of tripping it. Fail with the offending package name and the
    file that imported it.
    <!-- planner-discipline-allow: analytics, ad-tech -->

    Seed the denylist from the categories PROJECT.md's Out of Scope table names — ad-tech SDKs,
    third-party health analytics, data-sale integrations — and make it a data file rather than
    inline constants, so adding a family later is a one-line change with a clear diff.

    **Assertion B — no new network surface.** Phase 3 has no backend by design; the research's
    responsibility map marks the API tier not applicable, and the reason is the locked privacy
    constraint. Record the network surface that exists as of the start of this phase in
    `ops/ci/allowed-network-surface.json` — the Worker routes and D1 tables Phase 2 left behind — and
    fail CI if the tree contains a route or migration not in that file.

    This is the assertion that turns "health records never leave the device" from a sentence in a
    document into a build failure. Anyone who genuinely needs a new route in a later phase updates
    the allowlist deliberately, in a reviewable commit, which is the entire point.

    Wire both assertions as a CI job.
  </action>
  <verify>
    <automated>node ops/ci/privacy-guard.mjs</automated>
  </verify>
  <acceptance_criteria>
    The guard passes on the current tree.
    Temporarily adding a denylisted package name to `package.json` makes it exit non-zero naming that
    package; removing it restores green.
    Temporarily adding a Worker route absent from the allowlist makes it exit non-zero; removing it
    restores green.
    Adding a source comment containing a denylisted name does not change the guard's result, proving
    the gate reads structure and not free text.
    The guard runs as a CI job on every push.
  </acceptance_criteria>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry -> dependency tree | Third-party code enters a health application on every install |
| repository -> network surface | A new Worker route or D1 table would move health data off the device |
| clean checkout -> native binary | A native patch that is not reapplied silently reverts a privacy guarantee |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-13 | Information Disclosure | package.json dependency tree | high | mitigate | Structural denylist over parsed dependency keys and import statements, enforced on every push. |
| T-03-14 | Information Disclosure | Worker routes / D1 migrations | critical | mitigate | Allowlisted network surface recorded as a data file; any addition fails CI and requires a deliberate reviewable commit. |
| T-03-15 | Tampering | node_modules native source | high | mitigate | patch-package postinstall hook, verified by a delete-and-reinstall cycle, so plan 03-05's patch cannot silently revert. |
| T-03-16 | Information Disclosure | Android app data directory / iOS app container | critical | mitigate | Device smoke pulls the Android data directory and inspects the iOS app container, confirming no raw key material exists outside the platform keystore on either. The iOS Keychain item is additionally confirmed to carry a device-only accessibility class so the key is excluded from device backups. Where the iOS-runner answer is "ios-deferred", the iOS half is recorded as pending rather than assumed. |
| T-03-17 | Denial of Service | CI Android build | low | accept | A broken Android toolchain blocks the build job, which is the intended behaviour — this is the failure PROJECT.md wants surfaced early rather than during a build session. |
</threat_model>
