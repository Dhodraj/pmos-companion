<objective>
Build the notification layer as a set of things the product cannot do: it cannot send a generic
engagement prompt, it cannot send a third notification in a day, it cannot send anything during
quiet hours, and it cannot reference a streak.

Purpose: PROJECT.md records that this cohort carries roughly four times the general depression rate
and will lapse, and that shame accelerates uninstalls. Notification restraint is not a polish item
for this product; it is part of the safety posture. Building the restrictions as structural
properties — rather than as guidelines a future contributor might not read — is the only version
that survives contact with a growth conversation.

Output: a native scheduling bridge, a content gate, a quiet-hours window and a capped scheduler.

Owner: Dhodraj Sundaram. The user-facing quiet-hours control is Belson's and lands in plan 03-08;
this plan owns the storage key, the format and the enforcement.
</objective>

  <files>src/core/notifications/gate.ts, tests/notifications/content-gate.test.ts</files>
  <behavior>
    - A payload built from a personal insight bound to her own data is accepted.
    - A payload built from a due action she can take is accepted.
    - A payload with neither cannot be constructed — the constructor requires one of the two as a
      discriminated input, so a generic engagement prompt has no representation.
    - A payload whose body text references a streak, a broken streak, a missed day or a completion
      percentage is rejected, checked against the payload's own text at construction.
    - The accepted payload type is the only type the scheduler will take.
  </behavior>
  <action>
    Model the notification payload so the requirement is a type property rather than a rule.

    The constructor takes a discriminated union with exactly two variants: a personal insight, which
    carries a reference to the record or finding it came from, and a due action, which carries the
    action she can take. There is no third variant and no constructor overload that takes bare text.
    NOTF-01 says every notification carries a personal insight or a due action; the cleanest way to
    make that permanently true is to leave no way to express anything else.

    Then add a text assertion at construction for NOTF-03's prohibition. This is belt-and-braces —
    no streak field exists in the schema, so there is nothing to interpolate — but a hand-written
    string can still say it, and this catches that. Keep the check on the payload's own text, which
    is a value the gate holds, not on source files.

    Export the accepted payload as an opaque type. The scheduler in Task 3 accepts nothing else, so
    there is no path from arbitrary text to a scheduled notification.

    Write `tests/notifications/content-gate.test.ts` first, one case per behavior above, including a
    compile-level assertion that a bare-text construction does not type-check.
  </action>

  </verify>

  <files>src/core/notifications/quiet-hours.ts, src/core/notifications/scheduler.ts, tests/notifications/scheduler.test.ts</files>
  <behavior>
    - Scheduling a third notification for a day that already has two is refused, and the refusal is
      a returned value rather than a thrown error.
    - A notification whose delivery time falls inside the quiet-hours window is refused or deferred
      to the next moment outside it, and which of the two happens is a property of the payload — a
      due action defers, an insight is dropped.
    - A quiet-hours window that crosses midnight is handled correctly, since that is the common case.
    - With no quiet-hours window set, a sensible default window applies rather than no window at all.
    - The daily count is derived from the OS's currently-scheduled list plus a delivered log, not
      from a counter this module maintains independently.
  </behavior>
  <action>
    `quiet-hours.ts` reads and writes the window through Capacitor Preferences — a small setting that
    does not belong in the relational schema. Fix the storage key and the time format here and
    record both in the summary, because plan 03-08's settings screen writes the same key and a
    mismatch between the two halves is silent.

    Default the window rather than leaving it unset. A user who never opens settings should still not
    be woken up, and NOTF-02's requirement is that quiet hours are user-controlled, not that they are
    user-initialised.

    Handle the midnight crossing explicitly. A window from evening to morning is the normal
    configuration and the naive start-less-than-end comparison gets it exactly backwards.

    `scheduler.ts` takes only the gate's payload type. Before scheduling it checks the cap by asking
    the OS what is already scheduled and consulting a delivered log, rather than trusting a counter
    of its own — a counter drifts the first time the app is killed mid-write, and the drift is
    invisible until she gets four notifications in a day.

    Refusals return a value. A scheduler that throws when it hits its own cap turns a designed
    behaviour into an error path someone will later wrap in a try-catch and ignore.

    Write `tests/notifications/scheduler.test.ts` first, with the native bridge mocked, covering
    every behavior above including the midnight-crossing window.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-24 | Information Disclosure | notification body text on a lock screen | high | mitigate | The gate's payload variants carry a reference to the source record, not its contents; body text is composed to be meaningful to her without disclosing a symptom or a cycle state to someone reading her lock screen over her shoulder. This matters specifically for users whose phones are not private. |
| T-03-25 | Tampering | src/core/notifications/gate.ts | medium | mitigate | The payload type admits only insight-backed and due-action variants, so arbitrary text has no path to the scheduler. |
| T-03-26 | Denial of Service | daily cap counter | medium | mitigate | Count derived from the OS scheduled list and delivered log rather than an independently maintained counter that drifts on an app kill. |
| T-03-27 | Denial of Service | OEM battery manager killing the app | medium | accept | Delivery is owned by the OS scheduler, which is the correct mitigation; residual OEM-specific suppression is accepted and is a known property of budget Android devices this product targets. |
