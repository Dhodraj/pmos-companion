<objective>
Give her voice check-in in English with the audio genuinely never leaving the phone — by patching
the native layer to use an on-device recognizer, not by hoping a configuration flag is honoured.

Purpose: research finding #1 is the single most consequential finding of this phase. The Web Speech
API does not work inside Capacitor's WebView on either platform, and the only Capacitor-6-compatible
plugin exposes no way to force on-device recognition. The obvious implementation is a dead end that
fails silently by shipping audio to a cloud service. This plan closes that.

Output: a native patch, a fail-closed availability gate, a voice affordance in the check-in, and a
recorded radio-off verification procedure.

Owners: Dhodraj Sundaram writes the native patch and the availability gate, per assumption A-03 in
plan 03-01 — the guarantee at stake is "does audio cross the network", which is a data-plane
property. Belson Johnson builds the voice affordance in the check-in. Rahul Ramakrishnan supplies
the devices and the reinstall verification. Satheeshkumar runs the radio-off protocol.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: The on-device voice guarantee — one-way door</name>
  <decision>
    Is "audio never leaves the phone" enforced by native code, or established empirically by testing
    devices with the radio off?
  </decision>
  <context>
    Research established three facts and one gap. The facts: the Web Speech API is non-functional
    inside Capacitor's WebView on Android (never implemented in Android System WebView) and on iOS
    (WebKit bug 239816 — the object is exposed but the feature does not work, so feature detection
    returns a false positive). `@capacitor-community/speech-recognition@6.0.1` is the only release
    peer-compatible with the locked Capacitor 6 core, and its options interface is language,
    maxResults, prompt, popup and partialResults — there is no on-device or offline option anywhere
    in it. Every plugin that does expose such a flag requires Capacitor 7, or lives behind a paid
    private registry.

    The gap: which remediation the team takes is a genuine engineering decision, and research flagged
    its own fallback option as "the highest-stakes assumption in this document."

    This is a one-way door in the direction that matters. Shipping the weaker guarantee and
    strengthening it later means every user who used voice in the interim did so under an assurance
    the product could not actually make — and PRIV-05's language is "never uploaded under any
    configuration", which is not a claim a per-device test can support for untested hardware.

    The planner's recommendation is option-a-native-patch, recorded as assumption A-02, on three
    grounds. ADR-001 is LOCKED and already commits the team to native Swift and Kotlin plugins for
    sensing capabilities, so this is consistent with the architecture rather than additional to it.
    Android's offline-preference extra is documented as a hint that recognizers may ignore, so the
    weaker option cannot support a universal claim even on the devices it tests. And the empirical
    protocol is not discarded under this option — it is retained as the verification gate at Task 4,
    which is where a per-device test actually belongs.
  </context>
  <options>
    <option id="option-a-native-patch">
      <name>Native patch forcing an on-device recognizer (recommended)</name>
      <pros>The guarantee is structural. Android's on-device recognizer factory and iOS's on-device requirement flag are real capability constraints, not hints. Consistent with LOCKED ADR-001. Fails closed by construction on devices that cannot do it.</pros>
      <cons>Kotlin and Swift work inside a third-party plugin. Depends on plan 03-04's patch reproducibility hook. Excludes voice on Android below API 31, which is a real and stated product loss.</cons>
    </option>
    <option id="option-b-stock-plus-radio-off">
      <name>Stock plugin, radio-off empirical verification only</name>
      <pros>No native work. Reuses a verification protocol the team already committed to for the Phase 2 demo.</pros>
      <cons>Proves nothing about untested OEM and Android-version combinations, which is most of the Indian budget-phone market. Cannot support PRIV-05's "under any configuration" language. Research names this its own highest-stakes assumption.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a-native-patch or option-b-stock-plus-radio-off</resume-signal>
</task>

  <precondition>Plan 03-04's patch-package postinstall hook is wired and verified by a delete-and-reinstall cycle. Without it this patch reverts on the next clean checkout and the guarantee silently disappears.</precondition>
  <behavior>
    - The availability gate returns tap-only when the plugin reports the platform cannot do on-device
      recognition.
    - The availability gate returns tap-only when the availability call throws or returns an
      ambiguous result — unknown is treated as unavailable, never as available.
    - The availability gate returns tap-only when the microphone consent row is not granted, and it
      re-reads that row on every session rather than caching it.
    - The availability gate returns voice-enabled only when on-device capability is affirmatively
      confirmed and microphone consent is granted.
    - No code path in the module can start a recognition session without passing through the gate.
  </behavior>
  <action>
    Patch the plugin's native source so the recognizer it constructs is an on-device recognizer by
    construction.

    On Android: use the on-device speech recognizer factory introduced in API 31 rather than the
    general recognizer with an offline-preference extra. The extra is documented as a hint that
    recognizers may ignore, which is exactly the property that makes it unusable as a guarantee. On
    devices below API 31 the factory does not exist and the plugin must report the capability as
    unavailable. PROJECT.md sets the floor at Android 8.0, so this excludes voice on a slice of
    supported devices — that is a real and accepted product loss, and it is the correct trade against
    silently uploading a woman's voice. Record it in the summary as a stated consequence, not as a
    bug.

    On iOS: check the recognizer's on-device support property and set the request's on-device
    requirement flag. If on-device support is false, report the capability unavailable. The project
    floor is iOS 14 and the relevant APIs land in iOS 13, so no additional platform exclusion
    follows here. If plan 03-04's answer was that iOS is deferred, still write the Swift half of the
    patch — it must not be discovered missing later — and mark the iOS acceptance criteria as pending
    a runner rather than skipping the code.

    Save the result as a patch file so plan 03-04's postinstall hook reapplies it.

    Then write `src/core/native/voice.ts` as the only module in the codebase that imports the speech
    plugin. It exports one function that resolves the session mode, and one that runs a session.
    The gate is the seam: everything else calls through it.

    Fail closed, always. An unavailable capability, a thrown error, an ambiguous response, a missing
    consent row — every one of those resolves to tap-only. There is no branch anywhere that reaches
    a network-based recognizer as an implicit fallback, because the failure mode this whole plan
    exists to prevent is exactly a silent fallback that still returns a plausible transcript.

    Write `tests/voice/availability-gate.test.ts` first, with the plugin mocked at the module
    boundary and a case for every behavior listed above.
  </action>

  <action>
    Build `VoiceCapture` as a control inside the check-in. It calls `src/core/native/voice.ts` and
    never imports the speech plugin.

    Consent first. The microphone consent class is one of the six seeded at onboarding, all starting
    not-granted. Granting it is its own affirmative action with its own purpose text — it is not
    implied by having granted cycle and symptom consent, and PRIV-01 is explicit that consent is
    never a global flag. Re-read the row per session so a revocation takes effect immediately.

    When the gate says tap-only, render nothing. Absence is the right affordance: a greyed-out
    microphone invites her to ask why it does not work, and the honest answer — her phone cannot
    transcribe without sending audio somewhere — is a conversation the check-in screen is the wrong
    place for. Put that explanation in the consent screen's purpose text instead, where she is
    already reading about what the microphone would be for.

    The transcript writes into the symptom log as text. Nothing derives anything else from it and
    nothing keeps the audio. CHK-05 says voice is an input method and never a mood biomarker, and
    PROJECT.md's Out of Scope table records why that exclusion is permanent: cross-lingual transfer
    on voice affect collapses to roughly chance on a binary task and there is no Hindi or Tamil
    validation at all. This is not a feature deferred to a later phase; it is a thing this product
    does not do.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| microphone -> native recognizer | Raw audio exists momentarily; whether it crosses the network is decided here |
| native recognizer -> network | The boundary PRIV-05 says must never be crossed under any configuration |
| consent row -> recording session | A session must not start without an independently granted microphone consent |
