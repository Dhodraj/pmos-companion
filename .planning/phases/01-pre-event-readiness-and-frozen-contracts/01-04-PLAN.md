<objective>
Stress-test the three interface contracts against their actual consumer before they are frozen, and
do it while Belson is unblocked and everyone else is busy elsewhere.

Phase 1's first success criterion is that Belson can write every screen against `src/types/` without
waiting on Dhodraj. The only way to know that is true before Friday is for Belson to walk each screen
against the proposed types and say, in writing, which fields he needs and which are not there. Doing
that on Saturday morning is discovering the gap; doing it now is closing it.

01-RESEARCH.md's Code Examples give concrete, source-grounded sketches of `LogEntry`, `Finding` and
`ExportPayload`, each field quoted against the build-plan or PRD line that justifies it. Those
sketches are the input. This plan's output is the delta between them and what five real screens
actually need — and that delta is what plan 01-05 freezes against.

Owner: **Belson Johnson**, frontend only, both tasks. He touches no types, no engine, no toolchain.
He writes down what a screen needs.

Purpose: make the Friday freeze an informed decision instead of a hopeful one, and close OPEN-13's
allocation pressure by moving the thinking part of six screens into the pre-week.
Output: one document that plan 01-05 reads before Dhodraj signs the freeze.
</objective>

    Owner: Belson.

    Create `docs/contract-dry-run.md` in the team repo. It has one section per screen, in this order:
    check-in, insight card, doctor export view, cycle view, safety-layer screen.

    Each section carries a table with these columns: the element the screen renders, the type it
    reads from (`LogEntry`, `Finding` or `ExportPayload`), the specific field it needs, and a status
    of `present`, `missing`, `ambiguous` or `unrenderable`. Use `present` only when the field exists
    in the 01-RESEARCH.md sketch with a type that can be rendered directly. Use `ambiguous` when the
    field exists but its units, range or encoding are not stated — a severity number with no stated
    scale cannot be turned into a control. Use `unrenderable` when the field exists but the screen
    cannot show it without a value the type does not carry, for example a plain-language label where
    only a raw number is present.

    Specific things each section must resolve, because each is a place where a screen and a type
    typically disagree:

    - **Check-in.** CHK-01 requires the whole entry in thirty seconds median across bleeding, sleep
      timing, movement, mood, energy, skin, cravings, pain and medications. Walk that list against
      `LogEntry`'s fields and its symptom array and state, per dimension, what control renders it and
      what value range that control produces. CHK-03's same-as-yesterday shortcut needs to know what
      a previous entry looks like to copy it. CHK-05's voice entry writes into the same shape, so
      state whether a voice-originated entry is distinguishable from a tapped one and whether any
      screen needs it to be.
    - **Insight card.** This is the screen with the most at stake, since build-plan.md section 5 says
      the finding has the most dependents. Render both `Finding` variants. For `pattern-found`,
      NOF1-04 requires observation count and signal strength stated in plain language on every reveal,
      so state which field carries the plain-language form and which carries the raw statistic. For
      `still-learning`, write the complete card — not a degraded version of the other one — and note
      which fields it has and which it deliberately does not.
    - **Doctor export view.** Walk `ExportPayload` against DOC-01 through DOC-04. DOC-04 requires every
      app-derived value labelled a wellness trend rather than a clinical measurement; state where that
      label renders and confirm the payload carries it as a required value rather than something the
      view has to remember to add.
    - **Cycle view.** CYCL-02 requires a day count relative to her own historical range with no
      "late", "overdue", "missed" or pregnancy language, and CYCL-05 requires an interval
      distribution and a bleeds-per-year counter. State which type carries each, and note explicitly
      if a needed value is not in any of the three — that is a legitimate finding, not a failure.
    - **Safety-layer screen.** SAFE-02 and SAFE-03 require fixed, unpaywalled crisis text. State
      whether any of that text comes from a type at all. If it is entirely static copy with no type
      dependency, say so — that is the answer, and it means this screen never blocks on the freeze.

    Do not soften anything. A field that is not there is `missing` even when the screen could limp
    without it, and a scale that is not stated is `ambiguous` even when the obvious guess is
    probably right. This document is only useful to the extent it is uncomfortable.
  </action>

    Append a `## Gaps` section to `docs/contract-dry-run.md`. Every row in task 1 whose status is
    `missing`, `ambiguous` or `unrenderable` gets one numbered entry here. Each entry states, in this
    order: which screen and element it blocks, the exact field name and TypeScript type Belson
    proposes, which type it belongs on, and the one-line reason a screen cannot be built without it.

    Write these as proposals, not questions. "The insight card cannot render FR-404's plain-language
    strength from a bare number; propose `confidenceLabel` on the `pattern-found` variant" is
    actionable at the freeze. "How should strength be displayed?" is not, and turns into a
    conversation Dhodraj has to have on Saturday.

    Three constraints on what may be proposed:

    - Nothing that requires the not-enough-data case to be expressed as a null, an optional field or
      a boolean flag. HACK-01 rules that out explicitly and the research anti-patterns section
      explains why: it makes impossible states like a suppressed finding carrying a direction merely
      unlikely rather than unrepresentable.
    - Nothing that specifies how a value is computed. Belson's scope is frontend only. Propose that a
      field exists and what it must contain to be renderable; the statistics behind it are Dhodraj's.
    - Nothing that reduces what a screen must deliver. If a field is genuinely hard, it is still a
      gap entry with a proposed field. There is no deferral option in this document.

    Then add a `## Verdict` section answering one question in one paragraph: with these gaps closed,
    can Belson build all five screens against `src/types/` and hand-written fixtures without needing
    to speak to Dhodraj during the build? If the answer is no, name precisely what would still force
    a conversation. That sentence is the phase's first success criterion, and plan 01-06 will test it
    for real.

    Finally add a `## Freeze inputs` section listing, as a short checklist, each gap number and
    whether closing it changes `LogEntry`, `Finding` or `ExportPayload`. Plan 01-05 works from that
    checklist.
