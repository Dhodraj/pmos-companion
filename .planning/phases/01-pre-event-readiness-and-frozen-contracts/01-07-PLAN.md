<objective>
Produce the dataset the whole demo rests on, under a custody split that makes the pitch's one
unfakeable sentence true: *the person who wrote the engine did not know what was in the data.*

build-plan.md section 1 sets the protocol. Dhodraj writes the generator because he is the only one
who can. He does not choose what goes in it. Satheesh picks the planted pair from six candidates,
rolls the lag and the strength, runs the generator with a random seed, and hands Dhodraj the dataset
alone. The parameters stay sealed until the engine has reported at H10. Blindness needs the author
not to know the parameters; it explicitly does not need him not to know the code.

For that to be more than a verbal promise, the generator's shape has to make it mechanically true: a
pure function, parameters in, rows out, so Dhodraj can unit-test it against parameters he invents
while Satheesh is the only person who ever calls it with the real ones.

Two traps 01-RESEARCH.md verified and this plan closes. First, the null pair fails as a control if
both its variables happen to move with a shared cycle-phase process the generator models — the H10
gate would read that as a false positive through no fault of the engine. Second, if the output's
shape varies with which pair was planted, Dhodraj can infer the answer from the file.

Owner: **Dhodraj Sundaram** writes the generator and its tests. **Satheeshkumar** chooses the
candidates, rolls the parameters, runs it, and holds the sealed file. Nobody else is involved.

Purpose: HACK-02, and the negative control that matters more than the positive one.
Output: a deterministic generator, a determinism-and-leakage suite, six candidates, and a dataset
whose parameters exactly one person knows.
</objective>

<recorded_assumptions>
1. **Seeded PRNG comes from a library, not a hand-roll.** `Math.random` cannot be seeded in
   JavaScript at all, which makes it unusable for regenerating an identical dataset. `seedrandom` at
   3.0.5 is the pin — published 2019, roughly 8.4 million weekly downloads, official source repo — and
   is the safer default for something the blind test's credibility depends on than a five-line PRNG
   the team owns the correctness of under time pressure.
2. **Fourteen months is roughly 426 daily rows.** build-plan.md section 1 says fourteen months of
   history for a demo user. The exact row count is a generator parameter, but it is the same for every
   parameter set — see the schema-invariance requirement.
3. **This plan writes no statistics.** The lagged cross-correlation, the bootstrap intervals and the
   FDR correction are HACK-03 in Phase 2 and NOF1-02 in Phase 4. Phase 1 produces data shaped so a
   reasonable implementation of that statistic can recover the planted lag within a day either side,
   and nothing more.
4. **The sealed file lives outside both git worktrees.** Plan 01-01 already added a `.gitignore`
   entry as a second line of defence, but ignoring a file inside the repo is weaker than the file
   never being there. Satheesh's home directory or a USB stick, not the project tree.
5. **This plan shares one working tree with plan 01-06, on the branch `pre-event-scaffold`.**
   `health-team-311-war-room` is a sibling checkout outside GSD's worktree isolation, so the two
   wave-5 plans cannot each get a copy. They are safe together because neither moves HEAD and their
   file sets are disjoint — `tools/` here, `src/ui/` there — and because each stages explicit paths.
   The `seedrandom` install in task 1 is the one exception: it changes `package.json`,
   `package-lock.json` and `node_modules`, which plan 01-06 also reads. Do it once, early in task 1,
   before writing any generator code, so the window in which the tree is mid-install is as short as

    The determinism tests are the ones that matter if the dataset ever has to be regenerated: without
    them, a lost file means Satheesh re-rolling and the H10 gate testing something different from what
    was planned. Assert in-process equality, then assert cross-process byte identity by spawning a
    second `node` invocation that serialises the output and comparing the two strings.

    The leakage tests are the ones that protect the claim. For every pair of distinct
    `candidatePairIndex` values, and for at least three distinct `lagDays` values, assert the arrays
    have the same length and that the sorted key set of each row is identical across runs. Assert key
    *order* too, not just membership, since JSON key order is observable in a written file. If a
    future change makes the output shape depend on the planted pair, this suite is what catches it.

    The two recovery tests are a sanity check on the data, not an implementation of the engine. Write
    the crudest possible lagged-correlation probe inline — shift one series against the other across
    the one-to-fourteen window and take the correlation at each shift — and assert two things: on a
    candidate pair the probe generated with a known lag, the peak sits at that lag within a day either
    side; and on the null pair, no shift produces a correlation above a threshold stated in the test.
    If the second assertion fails, the generator is producing a null pair that is not null, and that
    is a task 1 bug to fix now rather than an H10 amber to discover on Saturday evening. Keep this
    probe inside the test file. It is not the engine, it does not move to `src/core/`, and HACK-03
