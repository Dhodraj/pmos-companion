  <action>
    Write `ops/seed.mjs`, a node script exporting `seed(datasetPath, target)` and runnable as
    `node ops/seed.mjs blindtest/dataset.json --target=<web|device>`.

    It reads a JSON array of `LogEntry`-shaped objects, validates every row against the frozen shape
    (id, ts, dayKey, cyclePhase, dimension, value, source) and rejects the whole file with a row
    index and the offending field if any row fails — a partially loaded dataset is worse than none,
    because the engine would then be reporting on data nobody can describe.

    `--target=web` writes the validated rows to `public/seed/dataset.json`, which the app loads once
    into Dexie on first launch when `?seed=1` is present in the URL or a `SEED_ON_BOOT` build flag is
    set. `--target=device` does the same and then runs the existing `android:debug` script so the
    seeded build lands on the phone in one command.

    The script must set `source: 'seed'` on every row it writes, regardless of what the input file
    says, so seeded rows are always distinguishable from rows a judge taps in live during the demo.
    That distinction is what lets the demo show a live entry landing in the same store as fourteen
    months of history without either being mistaken for the other.

    Print a one-line summary on success: row count, date range, and the distinct dimensions present.
    Do not print any per-row content — Rahul runs this and must not become a person who has seen the
    dataset's structure in a way that could leak toward Dhodraj.

    Extend `ops/README.md` with the two invocations.
  </action>
  <verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local machine → GitHub | Repo visibility is unresolved (OPEN-12); every commit may be public |
| CI runner → build artifacts | A third-party runner produces the artifact the team installs |
| keystore → release APK | Signing material grants the ability to publish as this app |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Information Disclosure | Keystore or env file committed to a possibly-public repo | high | mitigate | `.gitignore` hardened in Task 1 before any secret exists; automated gate asserts `git ls-files` lists no keystore or env file |
| T-02-11 | Tampering | CI step failure silently ignored | medium | mitigate | Automated gate rejects any `continue-on-error` in the workflow; every step is blocking |
| T-02-12 | Tampering | Partially loaded seed dataset producing findings nobody can describe | high | mitigate | `ops/seed.mjs` validates every row against the frozen shape and rejects the whole file on any failure |
| T-02-13 | Repudiation | Live demo entries indistinguishable from seeded history | medium | mitigate | Seed loader forces `source: 'seed'` on every row it writes |
| T-02-14 | Information Disclosure | Rahul learning the blind-test dataset's structure and leaking it toward Dhodraj | medium | mitigate | Seed summary prints counts and ranges only, never row content; sealed-parameter file pattern is git-ignored |
| T-02-15 | Elevation of Privilege | Release signing key usable by anyone with repo access | medium | accept | Single-weekend hackathon build with no store distribution; key stays on Rahul's machine and is never committed |
</threat_model>
