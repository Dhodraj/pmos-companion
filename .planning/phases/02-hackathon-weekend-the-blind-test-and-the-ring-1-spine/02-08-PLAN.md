<objective>
Ring 2: turn the export payload into a document a clinician would accept — one tap, under ten
seconds, entirely on the phone.

Purpose: HACK-05 is ring 2 in build-plan.md's ordering, and §13 puts the doctor export at step 5 of
the five-minute demo. Build-plan.md is explicit that this is spine, not slideware: §10 lists
"check-in, engine, insight card, export" as the four things that never get cut. This is the artifact
that turns eighteen months of lived experience into evidence a seven-minute consultation can absorb.

The labelling matters as much as the content. DOC-04 requires every app-derived physiological value to
be labelled explicitly as a wellness trend and not a clinical measurement — that line is what keeps
the document on the right side of the screen-and-refer boundary, and it is not a footnote to be added
later.

Output: a PDF on the demo phone, produced offline, that names the five tests she can ask for.

Owner: **Belson Johnson** for `src/app/ExportView.tsx`. `src/core/export/**` is Dhodraj's directory
and he completes the payload assembly and the renderer; Belson never edits it and Dhodraj never edits
the view (build-plan.md §2, §3).
</objective>

    Complete `buildExportPayload(entries, findings, range?)` so every field of the frozen
    `ExportPayload` is populated from real rows.

    `cycleHistory`: group `bleed_flow` rows into runs of consecutive days with a value above zero,
    emit one entry per run with its start date, the interval to the next run's start as `lengthDays`,

    from self-reported logging and is not a clinical measurement. Fixed text, written once, never
    generated.

    with no bleeds logged and no medication still gets a valid export — labs and history are never a

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dexie rows → document | Health data leaves the app's control as a shareable file |
| app → platform share sheet | The user chooses an arbitrary destination for that file |
| document → clinician | The strongest claim the product makes, read by a professional |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-39 | Repudiation | App-derived values read as clinical measurements | critical | mitigate | Fixed wellness-trend disclaimer rendered on every page; asserted by the extracted-text test, not by one header line |
| T-02-40 | Repudiation | A pattern claim in the document with no observation count | critical | mitigate | Every finding line states its count and strength; `insufficient_data` renders as "still learning" with no pattern claim, asserted by test |
| T-02-41 | Information Disclosure | Health data leaving the device during export | high | mitigate | `renderPdf` and `ExportView` are gated by automated no-I/O assertions; generation is entirely client-side and verified in flight mode |
| T-02-42 | Information Disclosure | Generated PDF persisting in a world-readable location | medium | mitigate | Written to the app's cache directory via the Capacitor Filesystem plugin, not to external storage |
| T-02-43 | Denial of Service | An 18-month payload exceeding the ten-second budget on stage | medium | mitigate | Symptom timeline rendered as a monthly summary rather than a per-row dump; the ten-second budget is an asserted test, not an aspiration |
</threat_model>
