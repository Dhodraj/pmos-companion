<objective>
Fire the tracer bullet: one thin path from a tap on the check-in screen, through IndexedDB, through
the correlation engine, to a rendered insight card and a serialized export payload — running on the
demo phone with the radio off.

Purpose: this is the ring 1 spine (HACK-04), the thing build-plan.md §10 says never gets cut. Proving
it end to end on the team's freshest hours means an architectural dead end costs one commit instead
of ten. The H4 gate at the end of this plan is build-plan.md's own first gate: "a check-in writes a
real row and the engine can read it back. Nothing else matters until data can move."

This is a tracer, not a prototype. Everything written here stays in the final system. Only two
things are deliberately thin: the engine returns a correlation over a single hard-coded candidate
pair (plan 02-04 expands it to the full scan with FDR and bootstrap CI), and the export payload
carries findings plus a symptom timeline (plan 02-08 renders it as a PDF). Both fill in without an
architectural change. No layer is stubbed out.

Output: the spine, committed, working on the phone.

    Wire ONE path through every layer this phase will touch. One entry point, no other call sites,

    **Dhodraj — `src/core/**` (he writes none of the two UI files below):**

    `src/core/db.ts` — Dexie 4 database `PmosCompanion`, version 1, store
    `logEntries: 'id, ts, dayKey, cyclePhase, dimension, [dayKey+dimension]'`, typed with
    `EntityTable<LogEntry, 'id'>`. Export `writeCheckIn(entries: Omit<LogEntry,'id'>[]): Promise<void>`
    which stamps uuids and `bulkPut`s inside one transaction, and rethrows a named error on quota
    failure rather than swallowing it.

    `src/core/engine/pairs.ts` — the candidate pair list the engine scans. For the tracer, export
    `TRACER_PAIR: [Dimension, Dimension] = ['sleep_hours', 'skin_severity']` and
    `CANDIDATE_PAIRS: Array<[Dimension, Dimension]>` seeded with that one entry. Plan 02-04 fills
    `CANDIDATE_PAIRS` with the real set; nothing else changes when it does.

    `src/core/engine/index.ts` — `runFindings(entries: LogEntry[]): Finding[]`. For each pair in
    `CANDIDATE_PAIRS`: pivot rows to two day-aligned numeric series on `dayKey`, scan lags 1..14 with
    Pearson correlation on the overlap, take the strongest |r|, and return `pattern_found` with
    `lagDays`, `direction`, `strength`, `observationCount` and a `confidenceBand` derived from the
    Fisher z-interval on r. Below `MIN_PAIRED_OBSERVATIONS = 20` return `insufficient_data`; above the
    floor but below `MIN_STRENGTH = 0.2` return `no_pattern`. Both thresholds are exported constants
    so plan 02-04 can replace the interval method with the bootstrap CI and the strength test with
    Benjamini-Hochberg FDR without touching the call sites.

    `src/core/useFindings.ts` — `useFindings(): Finding[] | undefined` using `useLiveQuery` from
    `dexie-react-hooks` over `db.logEntries.toArray()`, memoised through `runFindings`. This is the
    reactive seam: a write re-renders the card with no manual refetch. It contains no JSX and is
    data access, not UI.

    `src/core/phrase/templateSentence.ts` — `templateSentence(f: Finding): string`, a pure function
    with an exhaustive switch over the union closed by `assertNeverFinding`. `pattern_found` reads
    like "Your skin severity tends to rise about 3 days after a night of shorter sleep — 87
    observations, moderate signal." `no_pattern` reads "No relationship found between your sleep and
    your skin so far — 87 observations." `insufficient_data` reads "Still learning — 12 observations
    so far." It imports nothing that can perform I/O. Gemini phrasing arrives in plan 02-07 as a
    replacement for this string, never as a precondition for having one.

    `src/core/export/buildExportPayload.ts` — `buildExportPayload(entries, findings): ExportPayload`,
    filling `generatedAt`, `rangeStart`/`rangeEnd` from the row range, `symptomTimeline` from the
    rows, `findings` as given, `requestedTests` with the five named tests (fasting insulin, free
    testosterone, DHEAS, 75g OGTT, AMH), and `disclaimer` stating that app-derived values are
    wellness trends and not clinical measurements. `cycleHistory`, `intervalStats` and
    `medicationLog` are computed from whatever bleed and medication rows exist and return empty
    collections when there are none — an empty history is a correct answer, not a missing feature.

    **Belson — the three files under `src/app/` and `src/ui/`:**

    `src/app/routes.tsx` — a route table with two entries for now, `/` → CheckIn and
    `/insight` → the insight card view, using react-router. Later plans register their screens here.

    `src/app/CheckIn.tsx` — the tracer's single entry point: two one-tap severity controls, one for
    `sleep_hours` and one for `skin_severity`, and a Save button that calls `writeCheckIn` with
    today's `dayKey` and `cyclePhase: 'unknown'`. On success it navigates to `/insight`. On the
    thrown quota error it renders the error inline rather than failing silently. The full
    fifteen-dimension check-in arrives in plan 02-05; the write path it uses is this one.

    `src/ui/InsightCard.tsx` — consumes `useFindings()`, renders the first Finding through
    `templateSentence`, and handles all three variants plus the `undefined` first-render state with a
    skeleton. It accepts an optional `phrasedSentence?: string` prop which, when present, replaces
    the template string — that prop is how plan 02-07 layers Gemini on without the card ever
    awaiting it.

    Commit as one tracer commit. Then have Rahul build and install on the demo phone.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → Dexie | Untrusted numeric and free-text values enter local persistence |
| WebView → IndexedDB | All health data at rest on the device; nothing crosses the network on this path |
| demo phone → stage | The installed artifact is operated in public by a judge |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Tampering | `runFindings` fed malformed rows | medium | mitigate | `runFindings` filters non-finite values and rows whose `dimension` is outside the `Dimension` union before pivoting; a bad row is dropped, never coerced to 0 |
| T-02-06 | Information Disclosure | Health rows leaving the device | high | mitigate | Architecture decision in Task 1 keeps the whole spine local; automated gate asserts `templateSentence.ts` performs no I/O; `src/core/**` on this path imports no network client |
| T-02-07 | Denial of Service | IndexedDB quota exhaustion during the demo | medium | mitigate | `writeCheckIn` rethrows a named quota error and `CheckIn.tsx` renders it inline instead of failing silently |
| T-02-08 | Repudiation | A finding rendered with no observation count behind it | high | mitigate | `Finding` carries `observationCount` on every variant and `templateSentence` states it in every sentence — a claim with no count cannot be rendered |
| T-02-09 | Elevation of Privilege | WebView loading remote content | high | mitigate | Inherited from plan 02-01: bundled `webDir`, no remote host key; re-asserted by the flight-mode cold launch in this gate |
</threat_model>
