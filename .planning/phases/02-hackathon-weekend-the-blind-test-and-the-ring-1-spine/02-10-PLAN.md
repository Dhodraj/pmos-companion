<objective>
Prove the sentence Rahul owns: it runs on the demo phone. A clean install on a wiped device, the
whole path working with the radio off, an APK from every four-hour window, and a recording of a
working run that survives the phone failing on stage.

Purpose: HACK-11 and build-plan.md §14's definition of done — "a thing is done when it runs on the
demo phone from a clean install, works with the radio off if it is meant to, and someone other than
the author has used it without being told how. Not when it works on your laptop." The H22 gate is the
last point at which a broken build can still be traded for a known-good one, and §9 says that if it
fails, the last good APK becomes the demo build and everything after H22 is polish on top of it.

The recording is not a nice-to-have. Build-plan.md §10 makes it the thing that keeps the fallback demo
available: the engine on the seeded dataset, the recovered lag, the correctly empty null pair, and the
doctor export as a static file — presentable with no app and no phone at all.

Output: a clean-install pass on a wiped phone, an automated offline smoke suite wired into CI, and a
recorded working run.

Owner: **Rahul Ramakrishnan**, all three tasks. Nobody else touches `ops/` or CI. He is also the
person who enforces the no-new-complex-logic rule from H20 onward, because he will be the
clearest-headed person in the room (build-plan.md §4).
</objective>

## Trust Boundaries

| Boundary | Description |

| build artifact → demo phone | The binary presented on stage; a bad one cannot be fixed live |
| app → network absence | The condition HACK-11 asserts must change nothing on the spine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-48 | Denial of Service | A network dependency introduced late blanking the app offline | critical | mitigate | `ops/offline-smoke.test.ts` runs as a distinct CI step on every push; the H22 flight-mode clean install is the human confirmation |
| T-02-49 | Denial of Service | The demo phone failing on stage | high | mitigate | Recording of a working run in flight mode plus a static export PDF, both indexed and playable from the laptop with no phone |
| T-02-50 | Tampering | An unverified APK treated as a rollback point | high | mitigate | `ops/apk.sh --verify` installs and launches before marking a row `VERIFIED`; unverified rows are not eligible as the fallback build |
| T-02-51 | Repudiation | Claiming clean-install success without evidence | medium | mitigate | `ops/clean-install.md` is written step by step with timestamps during the gate, not reconstructed after |
| T-02-52 | Information Disclosure | Recording or static export carrying real personal data | medium | mitigate | Both are produced from the seeded blind-test dataset only; no real user data exists at this point in the project |
</threat_model>
