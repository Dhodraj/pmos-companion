<objective>
Build the capture experience out from the tracer's bare screen: a live pulse waveform that draws
itself as samples arrive, guidance that tells her what to do with her hand, and a capture path that
works with the screen reader on and the screen unseen.

Purpose: this is 30 seconds of a woman holding still with a torch against her fingertip, and the
research is explicit that most failures are postural — pressing too hard occludes the capillary bed,
cold hands weaken perfusion, movement destroys the signal. Coaching before and during the capture is
not decoration; it is the highest-leverage thing on the screen. The waveform is the second: it turns
a blank half-minute into visible evidence that something is being measured.

Output: a capture screen with a live waveform, guidance copy in one reviewable file, and a
non-visual path through the whole flow.
</objective>

  <name>Task 1: Capture session hook — stream, countdown, teardown</name>
  <owner>Belson Johnson (github: Belsonselva)</owner>
  <files>src/features/camera-vitals/hooks/use-capture-session.ts, src/features/camera-vitals/hooks/use-capture-session.test.ts</files>
  <read_first>
    - `packages/capacitor-plugin-ppg-camera/src/definitions.ts` — the frozen start, stop and per-frame sample event contract
    - `src/features/camera-vitals/types.ts` — the frozen result union
    - `src/features/camera-vitals/capture-screen.tsx` — the tracer's bare screen, which this hook replaces the inline logic of
  </read_first>
  <behavior>
    - Starting a session subscribes to the native sample event and moves the hook into a capturing state with a countdown that starts at 30 seconds.
    - Each arriving sample appends to a bounded rolling buffer for the waveform; the buffer never grows past the window it renders, so a long session cannot grow memory without limit.
    - Reaching the end of the countdown stops the native session exactly once and hands the collected array on for processing.
    - Unmounting mid-capture stops the native session and unsubscribes — a torch left on after the user navigates away is a bug with a battery and a trust cost.
    - A native error mid-capture moves the hook to the rejected branch with the interrupted reason rather than leaving the countdown running forever.
    - Backgrounding the app mid-capture stops the session; capture is foreground and user-initiated by locked decision, and a session that survives backgrounding is a defect.
  </behavior>
  <action>
Write the tests first against a mocked plugin, watch them fail, then implement the hook.

The hook owns the session lifecycle so no component has to: start, subscribe, buffer, count down,
stop, unsubscribe, and hand off. Everything the screen renders comes from what this hook exposes —
capture state, seconds remaining, the rolling sample window for the waveform, and the final result.

Bound the rolling buffer to the number of samples the waveform actually shows. The full array for
processing is accumulated separately and handed over once; the render buffer is a window. Two
buffers is not premature optimisation here — the waveform redraws on every frame at 30 per second
and must not re-render against a growing array.

Guarantee the teardown. Stop the native session on unmount, on background, on error, and on normal
completion, and make stopping idempotent so a double-stop is harmless. The failure this prevents is
a torch left burning after she navigates away, which costs battery and, more importantly, looks like
the app is still watching.

Expose no derived number from this hook. It hands over an array and a result; it does not compute or
surface a live heart rate. A live number ticking during capture is exactly the false precision this
feature is required not to present, and it is the specific thing an anxious user would fixate on.
  </action>

    - `.planning/phases/06-camera-vitals-fingertip-ppg/06-RESEARCH.md` — "Architecture Patterns", the note that the finger covers the lens so there is no camera preview and the live view is this component driven by the scalar stream
    - `src/features/camera-vitals/hooks/use-capture-session.ts` — the rolling window this component consumes
  </read_first>
  <behavior>
    - Given a window of samples, the component renders a path with one point per sample.
    - Appending a sample redraws with the trace advanced by one; the oldest sample leaves the window.
    - The trace auto-scales to the window's own range, so a weak signal is still visible as a shape rather than a flat line pinned to the axis.
    - With fewer samples than the window holds, it renders what exists rather than padding to a fake full trace.
    - With an empty window it renders a resting baseline, not an error and not a blank hole.
    - The component exposes no axis labels, no scale, no units and no numeric annotation of any kind.
  </behavior>
  <action>
Write the tests first, watch them fail, then implement.

Render the trace as an SVG path or a canvas draw, driven by the rolling window from the capture hook.
Auto-scale vertically to the window's own minimum and maximum — a fingertip signal's pulsatile
component is a small fraction of its DC level, and a fixed scale would render every real capture as a
flat line. Smooth the scaling across redraws so the trace does not jump when the range changes
slightly.

Give the trace no numbers. No beats-per-minute readout, no amplitude scale, no axis, no units. It is
a shape that says "something is being measured", nothing more. The reason is in the open clinical
question this phase ships over: the reviewing clinician was asked whether a visible pulse waveform is
reassuring or alarming for a population with roughly six times baseline anxiety, and never answered.
Until Plan 06-09 gets that answer, this component stays maximally neutral — a calm, steady trace,
not a medical monitor. Keep the visual language soft: no grid, no sweep line racing across the
screen, no colour that reads as alert.

Keep the redraw cheap. It runs 30 times a second on a phone at the bottom of the market; memoise so a
sample arriving does not re-render the whole screen, and confirm the enclosing screen does not
re-render per sample.
  </action>
