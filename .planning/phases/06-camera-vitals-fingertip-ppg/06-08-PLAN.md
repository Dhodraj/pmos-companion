<objective>
Land the reading where it belongs: an encrypted, phase-tagged measurement row on her device, and one
more input variable into the correlation engine she already owns — held to the engine's existing
confidence floor, with nothing raw persisted and nothing sensitive logged.

Purpose: the entire clinical argument in `docs/clinical/PPG-07-clinical-position.md` rests on one
claim — that this reading is treated as an n-of-1 input variable subject to the same honesty
standard as every other logged signal, not as a clinical marker. This plan is where that claim
becomes true in code or becomes false. If the reading bypasses the confidence floor, or gets special
treatment the engine gives no other input, the document the team sent to a clinician is inaccurate.

Output: the measurement type extension, an on-device store, an engine input adapter, and a
repository-wide check that health values do not leak into logs.
</objective>

    - `src/data/measurement-types.ts` and the surrounding store code from Phases 3 and 4 — the existing enumeration members and the naming convention they follow
    - `.planning/phases/06-camera-vitals-fingertip-ppg/06-RESEARCH.md` — "Open Questions" item 3, which records that these literals do not exist anywhere yet, and the Architectural Responsibility Map row on result persistence
    - `.planning/PROJECT.md` — the privacy constraints: encryption at rest with keys in the platform keystore, raw media never persisted beyond the processing window
  </read_first>
  <behavior>
    - An accepted result persists one row carrying both bounds, the confidence level, the capture timestamp, the cycle-phase tag, and the source identifying it as a fingertip camera reading.
    - The persisted row carries no scalar rate field, no sample array and no derived waveform.
    - A rejected result persists nothing at all.
    - Reading the row back returns exactly what was written, including the confidence level.
    - The row is written through the existing encrypted store used by other measurement kinds, not through a new storage path.
    - Two captures in the same session persist two distinct rows rather than overwriting.
  </behavior>
  <action>
Add the enumeration members for this reading's kind and source, following the exact naming
convention the existing members use. Do not invent a parallel convention because this is a camera
reading; it is a measurement like any other and the point of the whole design is that it is treated
as one.

Persist through the store earlier phases already built, reusing the established encryption pattern —
keys in the platform keystore, encrypted at rest. Do not add feature-specific encryption. A bespoke
crypto path for this one feature is both unnecessary and a new attack surface.

Persist the bounds and the confidence, never a scalar. The result type has no midpoint and the row
must not acquire one; a stored midpoint would immediately become the number every future consumer
reads, and the range would exist only in the UI.

Persist nothing on rejection. Not a failed-attempt row, not a timestamp, not a counter. A rejected
capture is a normal event that costs her nothing, and a stored record of it is the seed of exactly
the punitive mechanics the project's constraints forbid.

Discard the sample array once the result is computed. It does not go into the row, into a cache, or
into a debug store. The privacy constraint is that raw media never persists beyond the processing
window, and a 900-float array reconstructing her pulse trace is raw media by any honest reading.

Write the tests first, watch them fail, then implement.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Processing window → persistent storage | The point at which a transient physiological value becomes a durable health record on the device |
| App internals → logging, crash and analytics sinks | Sinks that routinely serialise more context than intended and may cross the network |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-31 | Information Disclosure | Raw sample array persistence | high | mitigate | The array is discarded once the result is computed and the row type has no field able to hold it; a stored pulse trace is raw media under the project's own privacy constraint. |
| T-06-32 | Information Disclosure | Logging, crash and analytics sinks | high | mitigate | A standing test drives accepted, rejected and crashing captures through spied sinks and asserts every payload is free of health values, including nested and serialised forms. |
| T-06-33 | Tampering | Confidence floor bypass for this input | high | mitigate | The adapter applies the engine's existing floor with no softer variant, asserted by a test; a bypass would make the clinical position document sent to a reviewer factually wrong. |
| T-06-34 | Information Disclosure | Bespoke encryption for this feature | medium | mitigate | Persistence reuses the established keystore-backed encrypted store; the diff adds no crypto code, avoiding a new attack surface for one feature's benefit. |
| T-06-35 | Repudiation | Stored record of failed attempts | medium | mitigate | Rejection persists nothing — no row, no timestamp, no counter — so no punitive mechanic can later be built on data this feature quietly accumulated. |
