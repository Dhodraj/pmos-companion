<objective>
Take the Android-only tracer to real coverage: build the iOS path to parity behind the same frozen
interface, implement the runtime device-capability probe on both platforms with fail-closed
semantics, and find out how torch, exposure lock and frame rate actually behave on named real phones
including one at the ten-thousand-rupee bar this product's whole hardware claim rests on.

Purpose: PPG-06 says the feature must not appear on a phone that cannot do this. The failure this
prevents is not a crash — it is a woman with anxiety at roughly six times baseline being handed a
capture screen that produces garbage or nothing on her specific phone, repeatedly, with no
explanation. The capability gate exists so that never happens, and it is only trustworthy if it is
based on what the hardware actually reports rather than on a list of model names that goes stale.

Output: an iOS path at parity, a fail-closed capability probe on both platforms, and a device matrix
with real measured rows.
</objective>

  <action>
Implement the Swift capture session so it satisfies the frozen interface with no additions and no
platform-specific extras. The JavaScript side must not be able to tell which platform it is talking
to except through the capability result.

Configure the rear camera device inside a `lockForConfiguration` block: set exposure mode to locked
where supported, white balance mode to locked where supported, focus mode to locked where supported,
and turn the torch on at full level. Guard each with its support check — a device that does not
support one of these locks is a capability failure, so record which lock failed and surface it
through the capability path rather than proceeding with an unlocked session that will produce a
hunting, useless signal.

Take frames through `AVCaptureVideoDataOutput` configured for 32-bit BGRA. In the sample-buffer
delegate, get the image buffer, lock its base address, compute the spatial mean of the red channel
across the frame respecting the row stride, unlock, and let the buffer go in the same callback.
Never retain a pixel buffer, never copy one into a property, never accumulate them.

Discard the first 30 frames exactly as the Kotlin path does, for the documented reason: an Apple
developer forum thread reports ISO continuing to drift for roughly the first second of recording
despite a prior lock call, and the reported workaround behaved differently across device
generations. This is not a single fixed bug to detect and route around; it is ongoing
device-generation-dependent behaviour, so the discard is unconditional on every device.

Emit each surviving frame's scalar plus its monotonic index over the bridge. Nothing else crosses.
A debug flag that ships a preview frame is not acceptable even temporarily — the finger is on the
lens, so there is nothing to preview, and the privacy constraint is absolute.

Write `PpgCaptureTests.swift` as an XCTest target covering what can be tested without hardware: that
the red-channel mean computed over a synthesised BGRA buffer with known values matches the expected
value including a non-trivial row stride; that the warm-up counter suppresses exactly the first 30
frames and passes the thirty-first; and that a session-configuration failure produces the
interrupted result rather than a crash.

  <action>
Implement the capability probe on Android in `CapabilityProbe.kt`. Query the actual camera
characteristics of the rear camera: whether a flash unit is present, whether auto-exposure lock is
available, whether auto-white-balance lock is available, and whether the device can deliver the
target frame rate. Return the frozen capability union's supported branch only when every one of
those is affirmatively true.

Do not branch on the Camera2 hardware support level. The level that guarantees full manual sensor
control is a materially higher bar than this algorithm needs — it only needs to lock the values the
camera already computed — and copying a commercial SDK's requirement for that level would exclude a
large share of exactly the budget Android fleet this product exists to serve. Equally, do not build
a device-model allowlist: the Android market this targets reshuffles faster than any list can track,
and an allowlist silently excludes every phone released after it was written.

Implement the same probe on iOS against the capture device's torch availability and its support for
each of the three lock modes.

Make it fail closed, everywhere. Any thrown exception, any timeout, any result the probe cannot
interpret resolves to the unsupported branch with the probe-failed reason. An inconclusive answer is
an unsupported answer. The consequence of a false negative is a woman not seeing a feature; the
consequence of a false positive is a woman being walked through a 30-second capture on a phone that
cannot do it, repeatedly, with no explanation — those costs are not symmetric.

Make the probe cheap and cacheable. It runs once, at first navigation toward the feature, and its
result is memoised for the session; it must not open a capture session or turn on the torch.

Write `src/features/camera-vitals/capability.ts` as the TypeScript wrapper. It calls the native
method, validates the returned shape before trusting it, memoises the answer, and catches everything
into the unsupported branch. Its unit tests cover: a well-formed supported response passing through;
each unsupported reason passing through; a rejected promise resolving to unsupported; a malformed or
partial response resolving to unsupported; and the memoisation calling native exactly once across
repeated calls.

Create `docs/device-fleet.md` with the matrix skeleton Task 3 fills in: a row per device with make,
model, chipset, OS version, approximate street price, probe verdict, whether the torch held steady
for the full capture, the frame rate actually delivered, the battery percentage consumed by one
capture, and a free-text observation column. Name the intended fleet explicitly as three rows to be
filled: one budget Android at or near the ten-thousand-rupee bar the product's hardware claim rests
on, one mid-range Android, and one iPhone at or near the iOS 14 support floor — plus the wiped demo
phone chosen in Phase 1 if it is not already one of those.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Camera hardware → native plugin | Raw pixel buffers enter process memory on both platforms and must be reduced and released inside the callback |
| Capability probe → feature visibility | The probe's answer decides whether an anxious user is offered a capture that her phone cannot complete |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-13 | Information Disclosure | Swift sample-buffer delegate | high | mitigate | Lock the base address, compute the mean, unlock and release within the same callback; the acceptance grep for image types across the iOS plugin directory is a standing gate against a debugging regression. |
| T-06-14 | Denial of Service | Capability probe returning inconclusive | high | mitigate | Every error, timeout and uninterpretable response resolves to unsupported; the wrapper's catch paths are covered by named tests so a future refactor cannot quietly change the default to supported. |
| T-06-15 | Spoofing | Native capability response shape | medium | mitigate | The TypeScript wrapper validates the returned union's shape before trusting it to gate UI, rather than casting the bridge response and rendering on it. |
| T-06-16 | Denial of Service | Sustained torch thermal throttling | medium | accept | OEM thermal firmware varies too widely to control; mitigated in effect by the detrending step absorbing slow amplitude drift, and made visible by recording torch steadiness per device in the fleet matrix. Accepted as a measured, documented device characteristic rather than a defect to fix in software. |
| T-06-17 | Tampering | Device-model allowlist drift | medium | mitigate | Prohibited outright — the probe reads capability keys and the acceptance criteria grep for model-name and hardware-level branching to keep it that way. |
</threat_model>
