<objective>
Take the Android-only tracer to real coverage on Android: implement the runtime device-capability
probe with fail-closed semantics, record the iOS deferral so it cannot be mistaken for an omission,
and find out how torch, exposure lock and frame rate actually behave on named real phones including
one at the ten-thousand-rupee bar this product's whole hardware claim rests on.

Platform scope, decided 2026-08-03: **Android is the only platform this phase builds and tests.**
No macOS machine exists on the four-person team, so the Xcode toolchain and a device-tested Swift
capture path are not available at any point in this phase. iOS is deferred, not cancelled — the
frozen `definitions.ts` contract from Plan 06-01 already anticipates a second implementation, so
picking iOS up later is an implementation job behind an existing interface, not a re-architecture.
Requirements PPG-02 and PPG-06 remain fully in scope and fully satisfiable on Android alone: PPG-02
(lock AE/AWB/focus before capture) is met by the Kotlin path, and PPG-06 (the feature must not appear
on a phone that cannot do this) is met — indeed met most strictly — by iOS resolving to unsupported.

Purpose: PPG-06 says the feature must not appear on a phone that cannot do this. The failure this
prevents is not a crash — it is a woman with anxiety at roughly six times baseline being handed a
capture screen that produces garbage or nothing on her specific phone, repeatedly, with no
explanation. The capability gate exists so that never happens, and it is only trustworthy if it is
based on what the hardware actually reports rather than on a list of model names that goes stale.

Output: a fail-closed capability probe on Android, a documented and test-backed deferral for iOS, and
a device matrix with real measured Android rows and an explicitly pending iOS row.
</objective>

  <action>
Implement the capability probe on Android in `CapabilityProbe.kt`. Query the actual camera
characteristics of the rear camera: whether a flash unit is present, whether auto-exposure lock is
available, whether auto-white-balance lock is available, and whether the device can deliver the
target frame rate. Return the frozen capability union's supported branch only when every one of
those is affirmatively true.

Do not branch on the Camera2 hardware support level. The level that guarantees full manual sensor
control is a materially higher bar than this algorithm needs — it only needs to lock the values the
camera already computed — and copying a commercial SDK's requirement for that level would exclude a
large share of exactly the budget Android fleet this product exists to serve. Equally, do not build
a device-model allowlist: the Android market this targets reshuffles faster than any list can track,
and an allowlist silently excludes every phone released after it was written.

Implement the probe on Android only. Do not write an iOS counterpart — see Task 1 for why. On iOS
there is no native implementation to call, so the bridge rejects the `checkCapability` call as
unimplemented and the wrapper's catch path resolves that to unsupported with the probe-failed reason.
That is the intended and sufficient behaviour for a deferred platform, and it is exactly the same
outcome the fail-closed rule already produces for an Android phone whose probe throws. Confirm it
deliberately rather than assuming it: one of the wrapper's named tests below simulates the native
rejection and asserts the unsupported result, so the deferred platform's behaviour is covered by a
test that runs on a Linux CI machine with no Apple hardware anywhere in the loop. Do not add a
platform check in the TypeScript wrapper to special-case iOS — the generic catch path already covers
it, and a hard-coded platform branch would have to be found and removed later when iOS ships.

Make it fail closed, everywhere. Any thrown exception, any timeout, any result the probe cannot
interpret resolves to the unsupported branch with the probe-failed reason. An inconclusive answer is
an unsupported answer. The consequence of a false negative is a woman not seeing a feature; the
consequence of a false positive is a woman being walked through a 30-second capture on a phone that
cannot do it, repeatedly, with no explanation — those costs are not symmetric.

Make the probe cheap and cacheable. It runs once, at first navigation toward the feature, and its
result is memoised for the session; it must not open a capture session or turn on the torch.

Write `src/features/camera-vitals/capability.ts` as the TypeScript wrapper. It calls the native
method, validates the returned shape before trusting it, memoises the answer, and catches everything
into the unsupported branch. Its unit tests cover: a well-formed supported response passing through;
each unsupported reason passing through; a rejected promise resolving to unsupported; a malformed or
partial response resolving to unsupported; and the memoisation calling native exactly once across
repeated calls. Name the rejected-promise test so it reads as the deferred-iOS guarantee it is —
it stands in for the unimplemented-method rejection an iPhone will produce at runtime, and it is the
only assurance available for that platform until a Mac exists.

Create `docs/device-fleet.md` with the matrix skeleton Task 3 fills in: a row per device with make,
model, chipset, OS version, approximate street price, probe verdict, whether the torch held steady
for the full capture, the frame rate actually delivered, the battery percentage consumed by one
capture, and a free-text observation column. Name the intended fleet explicitly as three rows to be
filled: one budget Android at or near the ten-thousand-rupee bar the product's hardware claim rests
on, one mid-range Android, and the wiped demo phone chosen in Phase 1 if it is a distinct device.

Add a fourth row for an iPhone at or near the iOS 14 support floor, and mark every one of its cells
`PENDING — iOS deferred 2026-08-03, no macOS machine on the team`. Keep the row rather than deleting
it: an absent row reads as an untested platform nobody thought about, while a row marked pending
reads as a known, dated, deliberate gap with an owner. Add a line under the matrix stating that the
iOS verdict is currently unsupported by construction, not by measurement.
