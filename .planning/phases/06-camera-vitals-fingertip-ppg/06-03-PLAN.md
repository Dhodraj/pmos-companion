<objective>
Build the front half of the signal chain the PRD froze in FR-301: validate what the bridge hands us,
remove baseline wander with smoothness-priors detrending at lambda 10, and bandpass it with a
fourth-order Butterworth between 0.7 and 3.5 Hz — with the filter's coefficients cross-validated
against an external scipy reference rather than trusted from a fresh derivation.

Purpose: filter-design mathematics has stability and gain-normalisation failure modes that look
right and are wrong, and a wrong filter corrupts every reading silently — it presents as "noisy
readings", never as a crash. Proving the coefficients against an oracle is the whole reason this
work is separated from the estimation step in Plan 06-06.

Output: three tested, deterministic, dependency-free TypeScript modules that turn a raw sample array
into a clean band-limited signal.
</objective>

The frame-index check is the important one and is easy to skip. Plan 06-01 discards 30 frames
natively because locked exposure is documented as not being honoured for roughly the first second on

sample, do not pad a short array. A capture that did not produce a clean array is a capture that
failed, and failure is the normal case in this feature — the honest move is to return the rejected
branch and let the user try again with guidance.

Keep this module dependency-free and synchronous. It runs once per capture on an array of roughly
900 floats.

    - Applied to a constant-valued array, the output is near zero everywhere and contains no non-finite value.
    - Output length equals input length; the operation does not trim edges.
    - The lambda parameter is honoured: a materially larger lambda removes less high-frequency content and a materially smaller one removes more, in the direction the method specifies, so a mis-wired parameter is caught.
  </behavior>
  <action>
Implement the Tarvainen et al. 2002 advanced detrending method — regularised least squares with a
second-difference penalty, which behaves as a time-varying high-pass filter whose cutoff is set by
the regularisation parameter. Read the method before implementing it; do not reconstruct it from the
research document's summary, which names the method but does not derive it.

Default the regularisation parameter to 10, matching the value the PRD froze, and expose it as an
argument so the tests above can vary it. Do not tune it against the fixtures to make a test pass —
the value is a frozen product decision, and a test that only passes at a different lambda is
evidence of an implementation bug, not a reason to change the parameter.

The naive formulation inverts a dense matrix the size of the signal. At 900 samples that is
tractable but wasteful; implement the banded solve rather than a general inverse, and keep the whole
operation comfortably inside the 3-second post-capture budget (NFR-103) with room to spare for the
rest of the chain.

Write the tests first from the behaviours above, watch them fail, then implement.

  </read_first>
  <behavior>
    - The designed numerator and denominator coefficients match the committed scipy reference to within a tight numerical tolerance, at the reference's sample rate and band edges.
    - The filter's impulse response matches the reference impulse response to within tolerance — coefficient equality alone does not prove the filtering loop applies them correctly.
    - A sinusoid inside the band passes through with most of its amplitude intact.
    - A sinusoid well below the low edge, and one well above the high edge, are both attenuated heavily.
    - Filtering the clean fixture leaves its dominant frequency unchanged.
    - The filter is applied in a way that does not introduce a phase shift that would displace detected peaks — apply it forward and backward, and assert that a symmetric input produces a symmetric output.
    - Output length equals input length.
  </behavior>
  <action>
Design the fourth-order Butterworth bandpass from the standard bilinear-transform formulation, at
the sample rate the capture actually delivers, with band edges 0.7 and 3.5 Hz. Then prove it: the
first two tests compare both the coefficients and the impulse response against the committed scipy
oracle. This is the point of the whole task — a fresh filter derivation that has not been checked
against an external reference is not trustworthy, and the failure mode is silent corruption of every
reading rather than an error anyone would notice.

Do not install the filtering library the research pass flagged. It carries no declared repository
and is effectively unmaintained, and adopting it would require a blocking human legitimacy check
that this approach makes unnecessary.

Apply the filter zero-phase, forward then backward, so peak positions are not displaced in time.
Peak detection in Plan 06-06 measures inter-beat intervals; a filter that shifts peaks by a
frame-dependent amount distorts those intervals in a way that is invisible in the averaged rate and
material for anything derived from beat-to-beat spacing later.

Handle the sample rate as an argument rather than a constant. Plan 06-04's device-fleet work may
find phones that deliver a rate other than 30, and a filter hard-wired to one rate would silently
mis-band on those devices. If the requested rate has no committed reference, the tests that compare
against the oracle should be skipped explicitly with a message, not silently passed.

Write the tests first from the behaviours above, watch them fail, then implement.
  </action>
