<objective>
Prove the whole Phase 4 spine end to end on one variable pair: her own check-in history in
IndexedDB → a Web Worker → a per-cycle-phase baseline → a lagged cross-correlation over 1-14 day
windows → a seeded bootstrap confidence interval → a Benjamini-Hochberg-corrected significance
gate → a `Finding` → a card on screen that either states the pattern with its observation count and
strength, or says "still learning".

Purpose: this is the tracer. Every later plan in this phase expands outward from the path this plan
proves. If the on-device Worker pipeline cannot produce a `Finding` the UI can render exhaustively,
that is a fact worth owning after one commit rather than after ten. The slice is production-quality
— the statistics are real, the determinism is real, the "still learning" state is real — it is thin
in *coverage* (one named pair), not in *quality*.

The doctor-export path (Plan 04-03) is a sibling vertical slice with its own end-to-end verify, not
a layer stacked on this one. It shares only the Dexie read.

Output: the engine module, its Web Worker host, the main-thread client API, the additively-extended
`Finding` type, the seeded blind-test fixture, and the insight card that renders both variants.
</objective>

```typescript
type SymptomDimension =
  | 'bleeding' | 'sleep' | 'movement' | 'mood' | 'energy'
  | 'skin' | 'cravings' | 'pain' | 'medication';

type ConfidenceLabel = 'weak' | 'moderate' | 'strong';

type Finding =
  | { status: 'pattern-found'; variableA: SymptomDimension; variableB: SymptomDimension;
      lagDays: number; direction: 'positive' | 'negative'; strength: number;
      confidenceLabel: ConfidenceLabel; observationCount: number; }
  | { status: 'still-learning'; variableA: SymptomDimension; variableB: SymptomDimension;
```

    Write `src/engine/analyse-pair.ts` exporting `analysePair(input): Finding`. It does five things
    for one named pair of symptom dimensions, in order. (1) Compute the per-cycle-phase baseline for
    each variable from this user's own rows only, grouped by the phase tag, using mean and standard
    deviation; where a phase holds fewer than 8 observations, shrink that phase to the user's
    whole-history baseline and record `baselineScope: 'own-whole-history'` on the result, because
    CYCL-03's oligomenorrhoea and amenorrhoea states mean some phases legitimately hold two or three
    days for months. No cross-user, cohort or published reference distribution is read anywhere in
    this file — the only inputs are rows belonging to the requested user id. (2) Rank-transform both
    baseline-deviation series and correlate the ranks, which is Spearman's rho and is the correct
    statistic for an ordinal 1-5 severity scale. (3) Search lags 1 through 14 by shifting series B
    forward and pairing on overlapping days only, requiring at least 3 paired days per lag, and
    select the lag with the largest absolute rho. (4) Compute a percentile bootstrap confidence
    interval over 1000 resamples of that best lag's paired series using a mulberry32 PRNG seeded
    from a stable hash of `userId + variableA + variableB`; reuse whatever seeded-RNG helper Phase 1
    built for the blind-test generator rather than adding a second seeding scheme. Store the seed on
    the finding. Never call `Math.random()` in this file — an interval that moves between sessions
    with no new data makes "how do you know that?" unanswerable. (5) Derive a two-tailed p-value
    from rho and n via `jStat.studentt.cdf`, apply the Benjamini-Hochberg step-up procedure, and gate
    on the FDR-adjusted p-value together with a minimum observation count of 12. Note that the tracer
    analyses a single pair, so the correction family here has size one and both candidate correction
    conventions coincide; Plan 04-02 decides the family for the full multi-pair sweep at a
    `checkpoint:decision`, and this file's `benjaminiHochberg` helper is written to take the family
    as its argument so that decision has somewhere to land.

    The gate reads the FDR-adjusted p-value and the observation count. It must not read the
    strength label. Strength is an effect-size band computed from absolute rho only after a finding
    has already cleared the gate; wiring the gate to strength lets a large coincidental correlation
    over a handful of days present itself as a confident pattern.

    Write `src/engine/engine.worker.ts` as the Web Worker entry point: it receives a pair request,
    opens the Dexie store directly (IndexedDB is a plain Web API inside a worker and needs no native
    bridge), loads that user's rows, calls `analysePair`, and posts the `Finding` back. No Capacitor
    plugin call appears in this file or anything it imports — plugin calls do not reliably reach
    native code from inside a worker. Write `src/engine/index.ts` as the main-thread client:
