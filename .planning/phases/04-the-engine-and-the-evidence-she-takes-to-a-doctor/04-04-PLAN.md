<objective>
Make the reveal answerable. She can ask "how do you know that?" and get the method in plain words
with her own numbers in it — because the finding came from a lagged cross-correlation with a
bootstrap interval and an FDR correction, and that chain is written down. And she gets a sentence
that reads like a person wrote it, phrased by Gemini from the Cloudflare Worker, on abstracted
numbers only, checked against the numbers the engine computed before it is shown, falling back to
the deterministic sentence the moment anything is off.

Purpose: this closes the third of the phase's four success criteria and puts a guarded boundary
around the only place in this phase where anything leaves the device. It also resolves an open gap
the research surfaced and left open: PRIV-01's six consent classes name nothing that covers sending
an abstracted numeric finding to a third-party model for phrasing. This plan resolves it rather than
leaving it — a seventh consent class, in the data plane, visible and revocable.

Output: the seventh consent class and its first-use disclosure, the Worker phrasing route with its
prompt and output guard, the consent-gated client seam, the "how do you know that?" panel, and the
model-phrased doctor-summary variant sitting in front of Plan 04-03's deterministic narrative.
</objective>

  <decision>Does sending an abstracted numeric finding to Gemini for phrasing get its own consent class, fold into the existing cycle-and-symptom class, or require an explicit opt-in before the first reveal is phrased?</decision>
  <context>
PRIV-01 requires purpose-bound granular consent per data class and names exactly six: cycle and
symptom data, camera sensing, skin images, mental-health screeners, mycyclesafe import, microphone.
None of them names "send an abstracted numeric finding to a third-party language model for
phrasing." The research found this gap and left it open. It has to be closed before a phrasing call
is wired into the reveal path, not after.

What actually crosses the network is small and abstracted: two symptom dimension names drawn from
the fixed curated set, a lag in days, a direction, an effect-size band, an observation count and a
confidence interval. No dates, no raw severities, no free text, no identifiers. It is her pattern,
not her record. But DPDP's purpose limitation is about the purpose, not the payload size, and
"phrased by a third-party model" is a materially different purpose from "stored on your phone so
the app can show you a cycle view."

This is a one-way door. Consent rows are written per user at onboarding and each row carries the
purpose it was granted for. Adding a class later means a schema migration over rows already written,
and defaulting a newly-added class to granted for users who never saw it is precisely the DPDP
failure Phase 3's own research flagged. The choice made here is the one every existing user's
consent ledger inherits.

Recommendation, and what this plan implements unless redirected: a seventh class, `ai_phrasing`,
defaulting to granted because what crosses is derived numbers rather than health records — paired
with a first-use disclosure sheet shown before the first phrasing request ever fires, naming
exactly what leaves the phone and carrying an immediate off switch. The disclosure is what makes
"default granted" defensible rather than silent: she is told at the moment of first use, not buried
in an onboarding flow she tapped through weeks earlier. Revoking it stops the request at the client
and the deterministic sentence is used, which is a complete product either way.
  </context>
  <options>
    <option id="seventh-class-default-on-with-disclosure">
      <name>Seventh class `ai_phrasing`, default granted, with a first-use disclosure and an immediate off switch (recommended)</name>
      <pros>Purpose-bound and independently revocable, which is what PRIV-01 actually asks for. The disclosure converts a default into an informed one. Reveals read naturally from day one. Revoking degrades to the deterministic sentence with nothing lost structurally.</pros>
      <cons>A newly-added class defaulting to granted is the pattern Phase 3's research warned about; the disclosure is what carries the defence, so the disclosure is not optional. Requires a Dexie schema version bump with an upgrade that seeds the row for existing users.</cons>
    </option>
    <option id="seventh-class-default-off">
      <name>Seventh class `ai_phrasing`, default not-granted, opt-in from the consent screen</name>
      <pros>The most conservative DPDP posture; matches Phase 3's rule that classes start not-granted. No defence needed for a default.</pros>
      <cons>Most users never open the consent screen, so almost every reveal reads as the deterministic sentence — the phrasing work ships but is never seen, and the team learns nothing about whether it helps.</cons>
    </option>
    <option id="fold-into-cycle-symptom">
      <name>Treat phrasing as covered by the existing cycle-and-symptom class</name>
      <pros>No schema change and no migration.</pros>
      <cons>Collapses two genuinely different purposes into one row, which is exactly what "purpose-bound, one row per class, never a global flag" forbids. She could not turn off the model without turning off the app.</cons>
    </option>
  </options>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Device → Cloudflare Worker | The first and only network crossing in this phase. Everything upstream of it is on device. |
| Cloudflare Worker → Gemini | A third party receives derived numbers and returns text that will be shown to her. |
| Model output → UI | Untrusted text entering a health surface. |
| Consent ledger → phrasing path | A revoked row must stop a network request, not merely hide a result. |
